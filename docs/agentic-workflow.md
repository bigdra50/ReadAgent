# エージェンティック開発の進め方

このリポジトリは Claude Code に実装させることを前提に構成しています。
「人がレビューできる速度」を超えて変更が積み上がらないようにするのが、この構成の目的です。

## ハーネスの構成要素

| 場所 | 役割 |
| --- | --- |
| `CLAUDE.md` | 全セッション共通の前提。コマンド・境界・規約。 |
| `.claude/settings.json` | 権限（allow / ask / deny）とフックの登録 |
| `.claude/hooks/` | 自動で走る安全網。下表参照 |
| `.claude/commands/` | 定型作業のスラッシュコマンド |
| `.claude/agents/` | 専門サブエージェント |
| `docs/` | 仕様と決定の一次情報 |

### フック

| フック | タイミング | すること |
| --- | --- | --- |
| `session-start.sh` | セッション開始 | 依存を揃え、ブランチ・差分・直近コミットを要約して渡す |
| `guard-bash.mjs` | Bash 実行前 | npm/yarn の使用、force push、main への直接操作、`.env` 閲覧を拒否 |
| `format-file.mjs` | ファイル編集後 | 触ったファイルだけ Biome で整形。直せない指摘は差し戻す |
| `verify-on-stop.mjs` | 応答終了時 | TypeScript を触ったターンなら型チェック。落ちていれば直させる |

フックは「Claude に守らせる」のではなく「守られている状態を機械的に作る」ためのものです。
規約をプロンプトで繰り返すより、フックで落とすほうが確実で、コンテキストも消費しません。

### スラッシュコマンド

| コマンド | 用途 |
| --- | --- |
| `/verify` | `pnpm run verify` を通し、落ちた箇所を直す |
| `/feature <要件>` | 要件の1スライスをテストから実装する |
| `/adr <決定>` | アーキテクチャ上の決定を ADR に記録する |
| `/ship [要旨]` | Conventional Commits でコミットし作業ブランチへ push |
| `/handoff` | 次のセッションへの引き継ぎメモを出す |

### サブエージェント

| エージェント | 用途 |
| --- | --- |
| `reviewer` | 実装が一段落したら、規約と要件に照らしてレビューさせる |
| `sdk-researcher` | Agent SDK や pdf.js の挙動を、記憶ではなく一次情報で確認させる |

## 標準の進め方

1. **要件を確認する** — `docs/requirements.md` の該当節。曖昧なら実装前に確定させる
2. **スライスを切る** — 1PRで完結する縦割り。広すぎるものは分ける
3. **`/feature` で実装** — 失敗するテストを先に書く
4. **`reviewer` にレビューさせる** — 自分で書いたものを自分で読み直させる
5. **`/verify`** — CI と同じものをローカルで通す
6. **`/ship`** — コミットして push
7. 決定が発生していたら **`/adr`**

## 効かせるための原則

- **セッションは短く保つ。** 文脈が長いほど、前提が薄まって精度が落ちます。
  区切りがついたら `/handoff` を出して新しいセッションを始めるほうが速い。
- **不確かなことは調べさせる。** SDK の API は記憶で書かせない。`sdk-researcher` か
  `node_modules/**/*.d.ts` の実物を根拠にする。
- **失敗を握りつぶさない。** CI やフックが落ちたとき、ルールを緩めて通すのは最後の手段。
  まず「なぜ落ちたか」を直す。
- **未決定を未決定のまま扱う。** `docs/architecture.md` の未決定事項は、
  勝手に決めて実装しない。ADR で決めてから書く。
