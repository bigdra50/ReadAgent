# spike: PDFの選択箇所をどう指し示すか

`docs/architecture.md` の未決定事項「選択箇所の永続的な位置指定」を決めるための実測。
ノートから本文へ戻るリンク（要件 3.3）が、PDFの再抽出や依存更新で壊れないかを確かめた。

## 環境

| | |
| --- | --- |
| pdf.js | `pdfjs-dist` 4.10.38 / 5.7.284 / 6.2.108 |
| ランタイム | Node 22.22.2、Chromium 141（Playwright 同梱ビルド） |
| 対象1 | tracemonkey 論文 14ページ（LaTeX 由来・2段組・英語）※ `pdf-parse` のテストデータ |
| 対象2 | 日本語サンプル 1ページ（見出し・2段組・コードブロック・箇条書き・脚注を含む） |

対象2は Chromium の print-to-PDF で生成したもので、**LaTeX や InDesign が出力する
日本語PDFとは字詰めの実装が異なる**。この点は下の「限界」に記す。

## 測ったこと

### 1. 抽出は決定的か

同じファイルを同一バージョンで2回抽出し、全ページの連結文字列を比較した。

**完全一致。** ハッシュまで同じ。抽出結果が実行ごとに揺れることはない。

### 2. pdf.js のバージョンを跨いでも同じか

| | 文字数 | テキストアイテム数 | 本文ハッシュ |
| --- | ---: | ---: | --- |
| 4.10.38 | 82,804 | 3,489 | `9e69b00ddac5` |
| 5.7.284 | 82,804 | 3,282 | `9e69b00ddac5` |
| 6.2.108 | 82,804 | 3,282 | `9e69b00ddac5` |

**本文は3バージョンで完全一致（不一致 0/14 ページ）。日本語サンプルも一致。**

一方で**テキストアイテムの数は 3,489 → 3,282 に変わった**（日本語は 81 → 57）。
つまり文字列は同じでも、アイテムの区切り位置は変わる。
`(アイテム番号, アイテム内オフセット)` でアンカーを保存すると、
pdf.js を上げただけで位置がずれる。

### 3. サーバ（Node）とブラウザで同じ文字列が得られるか

同じ抽出規則で組み立てたページ文字列を比較。**全ページで一致。**
サーバ側で抽出した本文と、ブラウザが描画したテキストレイヤは同じ座標系で語れる。

### 4. DOM の選択 ↔ 文字オフセット の往復は壊れないか

これが本題。ページ文字列を組むときに、pdf.js の `hasEOL` を見て改行を合成する実装が
広く使われている。その改行を**入れた場合と入れない場合**で往復を比較した。

DOM に対応する位置が無いオフセットの割合:

| ページ | 文字数（改行あり / なし） | 対応が無いオフセット |
| --- | --- | --- |
| tracemonkey p1 | 5,021 / 4,937 | 84（1.7%）→ **0** |
| tracemonkey p5 | 8,004 / 7,878 | 126（1.6%）→ **0** |
| 日本語 p1 | 535 / 511 | 24（4.5%）→ **0** |

対応が無かったオフセットは、**100% が合成した改行そのもの**だった。
テキストレイヤの各 span は絶対配置されており、DOM 側に改行文字は存在しないため、
合成した改行はどのテキストノードにも属さない。

オフセット → DOM選択 → オフセット の往復テスト（各ページ約400点）:

| ページ | 改行あり | 改行あり + 直前ノードへ寄せる | 改行なし |
| --- | --- | --- | --- |
| tracemonkey p1 | 407 OK / 12 NG | 415 OK / 4 NG | **412 OK / 0 NG** |
| tracemonkey p5 | 387 OK / 14 NG | 392 OK / 9 NG | **415 OK / 0 NG** |
| 日本語 p1 | 487 OK / 47 NG | 511 OK / 23 NG | **510 OK / 0 NG** |

失敗した範囲は、すべて合成改行を含むものだった。
近傍へ寄せる回避策では、復元した範囲が元と数文字ずれる（往復が非可逆になる）。
**合成改行を入れなければ、往復は全点で厳密に一致する。**

## 結論（設計ルール）

1. **正規のページ文字列は、テキストアイテムの文字列を連結したものだけとする。**
   `hasEOL` による改行を、この文字列に混ぜない。
2. **アンカーは `(page, start, end)` で保存する。** アイテム番号は使わない。
   本文はバージョン間で安定だが、アイテムの区切りは安定しないため。
3. **引用テキストはオフセットからサーバ側で切り出す。** ブラウザの
   `selection.toString()` を保存・送信に使わない。DOM には改行が無いため、
   正規テキストとずれる（実測で確認済み）。
4. **改行・ハイフネーションの結合は、表示とエージェント文脈の生成時に行う。**
   行情報はアンカーとは別に持つ。実際に `"discov-\nered"` のような
   行末ハイフンが観測されており、エージェントへ渡す前に結合する処理が要る。

## 実装での見え方

上の結論をそのまま実装した結果が下の画面。右ペインの `p.1 [4, 60)` が
保存されるアンカーで、その下の引用は**そのオフセットからサーバー側で切り出したもの**。
ブラウザの `selection.toString()` は送っていない（結論 3）。

引用の中で改行が復元されているのは表示のときだけで、正規のページ文字列には
改行が入っていない（結論 1・4）。

## 限界（未確認のこと）

- **日本語PDFは Chromium 生成の1ページしか試していない。** LaTeX（upLaTeX 等）や
  InDesign が出力する日本語PDF、縦書き、ルビは未検証。実際に読む書籍で再確認すること
- スキャンPDF（テキストレイヤなし・OCR）は対象外。別の設計が要る
- 段組をまたぐドラッグ選択の順序は未検証
- pdf.js の `TextLayer` クラスではなく、アイテムから自前で span を配置して検証した。
  実装時に `TextLayer` を使うなら、テキストノードとオフセットの対応を同じ方法で取り直すこと
- 検証スクリプトは使い捨てで、リポジトリには含めていない。再現に必要な情報は上記の環境と手順に記した
