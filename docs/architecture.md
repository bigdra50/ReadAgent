# アーキテクチャ

> 確定しているのは、レイヤ分割の原則（ADR-0003）と Phase 1 の実行形態（ADR-0004）です。
> UI フレームワークとノート周りの永続化は未決定で、下の表に残しています。
> 未決定事項を、決まったことのように実装へ持ち込まないでください。

## レイヤ

```
ブラウザ（Chromium 固定で開発）
┌─────────────────────────────────────────────┐
│ UI 層（分割ビュー: 目次 / 本文 / チャット・ノート） │
│  pdf.js のテキストレイヤ / 選択の取得              │
└──────────────────┬──────────────────────────┘
                   │ HTTP + SSE（localhost）
ローカル Node サーバー
┌──────────────────┴──────────────────────────┐
│ アプリケーション層                                │
│  セッション管理 / ストリーミング中継 / ジョブ制御      │
├──────────────┬──────────────────────────────┤
│ アダプタ層     │  PDF抽出 / ノート永続化 / Agent SDK  │
├──────────────┴──────────────────────────────┤
│ packages/core（純粋）                          │
│  ドメインモデル・設定解決・ノート構造の規則          │
└─────────────────────────────────────────────┘
```

依存の向きは常に**下向き**。`core` は上位層を知らない。

## なぜコアを純粋に保つのか

要件 2 で「第1優先はローカル完結、将来はWebサーバー化も検討可能な設計」とある。
この2つの実行形態の差は、**どこで副作用が起きるか**にほぼ集約される。

- ローカル: ノートはローカルファイル、Agent SDK はローカルプロセス
- サーバー: ノートはサーバー側ストレージ、SDK 実行もサーバー側、UI は HTTP/WS 越し

副作用をアダプタ層に閉じ込めておけば、この差は差し替えで吸収できる。
逆に、コアが `fs` や `fetch` を直接触った瞬間に、両立は破綻する。
テストが遅くなる・モックだらけになるのも同じ根から生じる。

## パッケージ

| パッケージ | 役割 | 状態 |
| --- | --- | --- |
| `packages/core` | ドメインモデル、設定の階層解決 | 実装済み（最小） |
| `packages/pdf` | PDFのテキスト抽出・目次抽出、引用の組み立て | 実装済み（最小） |
| `apps/server` | ローカルHTTPサーバー。本文の提供と、今後のエージェント中継 | 実装済み（最小） |
| `apps/web` | 読書UI（分割ビュー・テキストレイヤ・選択） | 実装済み（骨格） |
| `packages/agent` | Claude Agent SDK 連携、プロンプト組み立て、イベント変換 | 実装済み（最小） |
| `packages/notes` | Markdown ノートの組み立てと永続化 | 実装済み（最小） |

パッケージは**必要になった時点で**作ります。空のパッケージを先に並べません。

## 未決定事項（ADR で決める）

| 論点 | 選択肢 | 決める時期 |
| --- | --- | --- |
| UI フレームワーク | React / Svelte / その他 | Phase 1 着手時 |
| 選択箇所の永続的な位置指定 | ページ+文字オフセット（実測で推奨）/ テキストアンカー | Phase 2 着手時 |

最後の論点は特に重要です。PDFの再抽出やビューアの実装差でオフセットがずれると、
ノートから本文への双方向リンク（要件 3.3）が壊れます。
これは実測済みで、結果と設計ルールは [spike-pdf-text-anchor.md](spike-pdf-text-anchor.md) にあります。
要点は「ページ文字列に改行を合成しない」「アイテム番号でアンカーしない」の2つです。
保存形式そのものは、ノートの保存単位と合わせて Phase 2 で決めます。
