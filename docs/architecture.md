# アーキテクチャ

> 現時点で確定しているのは**レイヤ分割の原則**と `packages/core` の位置づけだけです。
> UI技術・プロセス構成・PDFレンダラの選定は未決定で、Phase 1 の着手時に ADR として決めます。
> ここに書かれた未決定事項を、決まったことのように実装へ持ち込まないでください。

## レイヤ

```
┌─────────────────────────────────────────────┐
│ UI 層（分割ビュー: 目次 / 本文 / チャット・ノート） │  未決定
├─────────────────────────────────────────────┤
│ アプリケーション層                                │
│  セッション管理 / ストリーミング中継 / ジョブ制御      │
├──────────────┬──────────────────────────────┤
│ アダプタ層     │  PDF抽出 / ノート永続化 / Agent SDK  │
├──────────────┴──────────────────────────────┤
│ packages/core（純粋）                          │
│  ドメインモデル・設定解決・ノート構造の規則          │
└─────────────────────────────────────────────┘
```

依存の向きは常に**下向き**。`core` は上位層を知らない。

## なぜコアを純粋に保つのか

要件 2 で「第1優先はローカル完結、将来はWebサーバー化も検討可能な設計」とある。
この2つの実行形態の差は、**どこで副作用が起きるか**にほぼ集約される。

- ローカル: ノートはローカルファイル、Agent SDK はローカルプロセス
- サーバー: ノートはサーバー側ストレージ、SDK 実行もサーバー側、UI は HTTP/WS 越し

副作用をアダプタ層に閉じ込めておけば、この差は差し替えで吸収できる。
逆に、コアが `fs` や `fetch` を直接触った瞬間に、両立は破綻する。
テストが遅くなる・モックだらけになるのも同じ根から生じる。

## パッケージ

| パッケージ | 役割 | 状態 |
| --- | --- | --- |
| `packages/core` | ドメインモデル、設定の階層解決 | 実装済み（最小） |
| `packages/pdf` | PDFのテキスト抽出・目次抽出 | 未着手（Phase 1） |
| `packages/agent` | Claude Agent SDK 連携、カスタムツール定義 | 未着手（Phase 1） |
| `packages/notes` | Markdown ノートの読み書きと双方向リンク | 未着手（Phase 2） |
| `apps/*` | 実行形態ごとの入口 | 未着手（Phase 1） |

パッケージは**必要になった時点で**作ります。空のパッケージを先に並べません。

## 未決定事項（ADR で決める）

| 論点 | 選択肢 | 決める時期 |
| --- | --- | --- |
| 実行形態 | Electron / Tauri / ローカルサーバー + ブラウザ | Phase 1 着手時 |
| UI フレームワーク | React / Svelte / その他 | 実行形態と同時 |
| PDF レンダリング | pdf.js（描画あり）/ テキスト抽出のみ | Phase 1 着手時 |
| Agent SDK の実行位置 | UIプロセス内 / 別プロセス | Phase 1 着手時 |
| ノートの保存単位 | 書籍1ファイル / エントリ1ファイル + インデックス | Phase 2 着手時 |
| 選択箇所の永続的な位置指定 | ページ+文字オフセット / テキストアンカー | Phase 2 着手時 |

最後の論点は特に重要です。PDFの再抽出やビューアの実装差でオフセットがずれると、
ノートから本文への双方向リンク（要件 3.3）が壊れます。決める前に実測してください。
