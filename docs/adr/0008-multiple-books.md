# 0008. 複数書籍はディレクトリで扱い、書籍IDはパスから決める

- **Status**: Accepted
- **Date**: 2026-08-10

## Context

Phase 4 で複数書籍に対応するにあたり、決めることが2つあった。

1. **どこから書籍を集めるか** — 明示的な登録簿を持つか、ディレクトリを見るか
2. **書籍をどう指すか** — ノートのアンカーと URL の両方で書籍を特定する必要がある

とくに2つ目は後戻りしにくい。IDが変わると、そのIDで保存したものが全部迷子になる。

## Decision

**書籍はディレクトリを見て集める。** 起動時に渡されたディレクトリ直下の PDF を
書籍として扱う。PDF ファイル1つを渡した場合は、それだけを含むライブラリとして扱う。
登録簿（データベースや設定ファイル）は持たない。

**書籍IDは絶対パスから決める。** `slug-<sha256の先頭8桁>` の形にする。
slug は ASCII の英数字だけを残したもので、日本語の書名ではハッシュだけになる。
表示名はファイル名から別に持つ。

一覧の順序や登録順に依存させない。書籍を1冊足しただけで既存のIDが変わると、
ノートも URL も一斉に壊れる。

## Consequences

- 書籍を足すのはファイルを置くだけ。登録の手順が要らない
- ID がパスから決まるので、同じ場所にある限り安定する
- **書籍を移動・改名すると ID が変わる。** そのときノートとの結びつきは切れる。
  ノートは書籍と同じディレクトリにあるので（ADR-0006）、一緒に動かせば実害は小さいが、
  改名だけをすると迷子になる。改名への追随が必要になったら、
  書籍側にIDを埋め込む方式（サイドカーファイル）を別の ADR で検討する
- ディレクトリを見るだけなので、階層をたどらない。書籍を入れ子に置くと見つからない
- 一覧のたびにディレクトリを読む。書籍が数百冊になったら、
  結果を保持する仕組みが要る。**いまは起きていない問題なので対処しない**

## Alternatives considered

- **登録簿を持つ（JSON や SQLite）** — 改名や移動に追随できるが、
  登録の手順が増え、実体と登録簿がずれる状態を扱うことになる。
  「ディレクトリに置けば読める」ほうが、この道具の使われ方に合う
- **書籍IDに連番やUUIDを使う** — 生成のたびに変わるか、登録簿が必要になる。
  パス由来なら、どちらも要らない
- **内容のハッシュをIDにする** — 移動・改名に強いが、全ページを読むまでIDが決まらず、
  一覧の表示にPDF全体の読み込みが要る。同じ本の版違いも別物になる
