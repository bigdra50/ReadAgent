# 0006. 読書ノートは書籍ごとに1つの Markdown ファイルへ追記する

- **Status**: Accepted
- **Date**: 2026-08-10

## Context

要件 3.3 はノートの形式を Markdown、永続化を「ローカルファイル（書籍単位）」と定めているが、
その中の持ち方は未決定だった（`docs/architecture.md`）。候補は2つ。

- 書籍ごとに1ファイル。エントリは見出しで区切って追記していく
- エントリごとに1ファイル + インデックス

判断の材料になるのは、このノートが**何のために存在するか**である。
要件 3.3 の内容例（引用原文、質問、回答、図解、関連リンク、タグ）と
要件 3.3 の双方向リンクからすると、これは検索用のデータベースではなく、
**後から通して読み返す1冊の記録**である。

## Decision

書籍ごとに1つの Markdown ファイルを持ち、エントリを追記していく。

- 既定のファイル名は `notes.md`（`resolveNoteConfig` の `notePath` で変更できる）
- エントリは `## ` 見出しで区切る。見出しにはページ番号と作成時刻を含める
- 本文への戻りリンクは、見出し直後に `<!-- readagent:anchor page=N start=S end=E -->` として埋め込む
- 追記は末尾へのみ行う。既存のエントリを書き換えない

コメント形式のアンカーを使うのは、Markdown として読んだときに邪魔にならず、
かつ機械が確実に取り出せるため。見出し文字列からページ番号を推測する方式は、
利用者がノートを手で編集した瞬間に壊れる。

## Consequences

- エディタでそのまま読める。`grep` も効く。Git で差分を追える
- 手で編集してよい。追記しかしないので、利用者の編集と衝突しにくい
- 1ファイルが際限なく伸びる。数千エントリの規模で開くのが重くなったら、
  章ごとの分割を別の ADR で検討する。**いまは起きていない問題なので対処しない**
- エントリ単位の検索・並び替えは、ファイルを読んで解析する必要がある。
  複数書籍の横断検索（Phase 4）でコストになりうる
- 追記しかしないため、同じ箇所への質問を繰り返すと似たエントリが並ぶ。
  整理はエージェントの仕事として Phase 4 に置く

## Alternatives considered

- **エントリごとに1ファイル + インデックス** — 検索と部分更新には向くが、
  通読できなくなり、ファイル数が読書量に比例して増える。
  「1冊の記録」という性格に合わない
- **SQLite などのデータベース** — 要件 3.3 が Markdown を指定しているため対象外。
  形式を変えると、利用者が自分のノートを他のツールで扱えなくなる
