# 0005. UI フレームワークに React を使う

- **Status**: Accepted
- **Date**: 2026-08-10

## Context

ADR-0004 で Phase 1 の実行形態をブラウザ + ローカル Node サーバーに決めた。
残っていたのが UI フレームワークの選定である。

このアプリの UI には、性質の異なる2種類の領域が同居する。

- **宣言的に書ける領域** — 目次、チャットの発言リスト、ノートペイン、ツール実行状況。
  状態から描画を導けばよく、フレームワークの得意分野である
- **命令的に触る必要がある領域** — pdf.js のテキストレイヤ。
  絶対配置された span の集合を自前で管理し、DOM の Selection / Range API を直接読む。
  `docs/spike-pdf-text-anchor.md` で確認したとおり、選択位置の取得は
  「テキストノードとオフセットを直に扱う」ことでしか成立しない

つまり、仮想DOMの外側に「フレームワークに管理させない DOM」を安全に置けることが要件になる。

## Decision

UI フレームワークは **React**、ビルドは **Vite** を使う。

pdf.js のテキストレイヤは、React の管理外の DOM として扱う。
具体的には `ref` で取得したコンテナに対して命令的に span を配置し、
React には再描画させない（`useEffect` の中で構築し、依存が変わったときだけ作り直す）。

## Consequences

- 仮想DOMの外に DOM を持つやり方（`ref` + `useEffect` + クリーンアップ）が
  React では定型化しており、テキストレイヤの実装を素直に書ける
- 情報量が多く、エージェントに実装させる際にも学習データの厚みが効く
- 分割ビュー・仮想スクロール・Markdown レンダリングなど、
  この先必要になる部品の選択肢が最も広い
- 一方で、テキストレイヤ周りは **React の外側**にあることを常に意識する必要がある。
  ここに `useState` を持ち込むと、選択のたびに再描画が走って選択が壊れる。
  この境界は実装時にコメントで明示すること
- Phase 3 でシェル（Electron / Tauri）を被せる場合も、React のコードはそのまま使える

## Alternatives considered

- **Svelte** — 記述量は少なく速いが、pdf.js のテキストレイヤのような
  「フレームワークに管理させない DOM」の扱いは React と同程度の手数になる。
  差が出ないなら、部品と情報量で React を採る
- **フレームワークなし（素の DOM）** — テキストレイヤだけを見れば最適だが、
  チャット・ノート・分割ビューの状態管理を自前で書くことになり、要件 4 の UI に対して割に合わない
