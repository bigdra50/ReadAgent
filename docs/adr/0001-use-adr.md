# 0001. アーキテクチャ上の決定を ADR として記録する

- **Status**: Accepted
- **Date**: 2026-08-09

## Context

このプロジェクトは実装の多くを Claude Code に任せる前提で進める。
セッションは有限で、過去の判断の経緯はセッションを跨いで残らない。
経緯が残らないと、同じ論点が繰り返し蒸し返されるか、
逆に理由を失った制約が惰性で守られ続けることになる。

また `docs/architecture.md` の時点で、実行形態・UI・ノートの保存形式など
重要な論点が未決定のまま残っている。これらは「なんとなく実装された結果」で
決まってしまいやすい部類のものである。

## Decision

アーキテクチャに影響する決定は `docs/adr/NNNN-<kebab-case-title>.md` に記録する。
`docs/adr/template.md` の構成に従い、`/adr` コマンドから作成する。

対象は、後から変えるコストが高い決定に限る。
具体的には、パッケージ境界、外部依存の選定、データの永続化形式、プロセス構成。
コーディング規約やライブラリのマイナーな使い分けは対象外とし、`CLAUDE.md` に書く。

決定を覆すときは、既存の ADR を書き換えず、新しい ADR を追加して
古いほうを `Superseded by ADR-NNNN` にする。

## Consequences

- 決定の理由がリポジトリに残り、新しいセッションが `docs/adr/` を読めば前提に追いつける
- 「なぜこうなっているのか」を人に聞く必要が減る
- 決定のたびにドキュメントを書くコストが発生する。
  そのため対象を「変更コストが高い決定」に絞り、些細な選択で ADR を書かせない

## Alternatives considered

- **コミットメッセージと PR 本文に残す** — 検索性が低く、決定が却下案や制約とともに残らない
- **単一の設計ドキュメントを更新し続ける** — 現在の姿は分かるが、なぜそうなったかの履歴が消える
