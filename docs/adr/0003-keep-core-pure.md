# 0003. packages/core を副作用から隔離する

- **Status**: Accepted
- **Date**: 2026-08-09

## Context

要件 2 は「第1優先はローカル完結、将来はWebサーバー化も検討可能な設計」としている。
この2形態の違いは、突き詰めると**副作用がどこで起きるか**の違いにほぼ集約される。

- ローカル: ノートはローカルファイル、Agent SDK はローカルプロセスで実行
- サーバー: 永続化はサーバー側、SDK もサーバー側、UI とは HTTP/WS 越し

加えて、要件 3.3 のノート更新はバックグラウンドで非同期に走り、キャンセル可能である必要がある。
非同期処理とI/Oがドメインロジックに混ざると、この部分のテストが遅く不安定になる。

## Decision

`packages/core` に、ファイルシステム・ネットワーク・Claude Agent SDK・UI への依存を持ち込まない。
`node:fs` や `fetch` を core が直接呼ぶことを禁止する。

core が置くのは、ドメインモデル（`Book` / `Selection` / `NoteEntry`）、
設定の階層解決、ノート構造の規則といった純粋な判断だけとする。
外部とのやり取りが必要な箇所は、core 側にインターフェースを定義し、
実装はアダプタ層（`apps/*` および将来の `packages/*-adapter`）に置く。

## Consequences

- ローカル版とサーバー版でコアを共有でき、差分をアダプタの差し替えに閉じ込められる
- core のテストが速く、I/O のモックを必要としない
- 「モックが増えてきた」ことが、境界を切り損ねた明確なシグナルとして機能する
- 単純な機能でも、インターフェース定義と実装の2箇所を触ることになり、行数は増える
- Phase 1 の時点ではサーバー版の実体が無いため、この制約は**将来のための前払い**である。
  払う価値があると判断したのは、後から副作用を剥がすコストのほうが明確に高いため

## Alternatives considered

- **まずローカル版を素直に作り、必要になったら分離する** — 実行形態の差はコード全体に薄く広がるため、
  後からの分離は事実上の書き直しになる
- **最初からサーバー・クライアント分離で作る** — Phase 1 の MVP には過剰で、
  ローカル完結という第1優先を遅らせる
